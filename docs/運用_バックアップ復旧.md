# DOSL HUB バックアップ・復旧ランブック

更新日: 2026-07-16

## 目標

- SQLite: 毎時フルバックアップ、RPO 1時間以内
- GCE永続ディスク: 日次スナップショット、14日保持
- SQLiteバックアップ: 専用GCSバケットで30日保持、Soft Delete 14日
- 障害発生から4時間以内にDBとサービスを復旧する

アップロード書類は既存の`dosl-hub-documents`バケットで管理する。DBバックアップは
権限と障害ドメインを分けるため、`dosl-hub-01-db-backups`へ保存する。

## 初回設定

GCP設定は外部変更を伴うため、承認後にローカルから実行する。

```bash
cd /Users/alltokyo42/Projects/exhibition-systems/document-management
bash deploy/configure_gcp_backups.sh          # dry-run
bash deploy/configure_gcp_backups.sh --apply  # 承認後のみ
```

VMの`/opt/dosl-hub/backend/.env`へ次を追加する。値はgitへ保存しない。

```dotenv
BACKUP_GCS_BUCKET=dosl-hub-01-db-backups
BACKUP_GCS_PREFIX=sqlite/hourly
BACKUP_LOCAL_RETENTION_HOURS=48
```

コード反映後、VM上でtimerを配置する。

```bash
sudo install -m 0644 /opt/dosl-hub/deploy/dosl-hub-backup.service /etc/systemd/system/
sudo install -m 0644 /opt/dosl-hub/deploy/dosl-hub-backup.timer /etc/systemd/system/
sudo mkdir -p /opt/dosl-hub/data/backups
sudo chmod 700 /opt/dosl-hub/data/backups
sudo systemctl daemon-reload
sudo systemctl enable --now dosl-hub-backup.timer
sudo systemctl start dosl-hub-backup.service
```

初回バックアップを必ず確認する。

```bash
sudo systemctl status dosl-hub-backup.service --no-pager
sudo journalctl -u dosl-hub-backup.service -n 100 --no-pager
sudo systemctl list-timers dosl-hub-backup.timer --no-pager
gcloud storage ls gs://dosl-hub-01-db-backups/sqlite/hourly/
gcloud compute resource-policies describe dosl-hub-daily-snapshots \
  --project=dosl-hub-01 --region=us-west1
```

## SQLite復元

本番DBを置換する前に、必ず一時パスで整合性を確認する。

```bash
RESTORE_DIR="$(mktemp -d)"
gcloud storage cp \
  gs://dosl-hub-01-db-backups/sqlite/hourly/<backup>.sqlite3 \
  gs://dosl-hub-01-db-backups/sqlite/hourly/<backup>.sqlite3.sha256 \
  "$RESTORE_DIR/"

cd /opt/dosl-hub/backend
sudo .venv/bin/python scripts/restore_sqlite.py \
  --backup "$RESTORE_DIR/<backup>.sqlite3" \
  --checksum-file "$RESTORE_DIR/<backup>.sqlite3.sha256" \
  --destination "$RESTORE_DIR/verified-exhibition.db"
sqlite3 "$RESTORE_DIR/verified-exhibition.db" "PRAGMA integrity_check;"
```

検証が`ok`になった後だけサービスを停止し、置換する。

```bash
sudo systemctl stop dosl-hub

# 障害時点のDBも退避する。GCS送信に失敗してもローカル退避は残す。
sudo /opt/dosl-hub/backend/.venv/bin/python \
  /opt/dosl-hub/backend/scripts/backup_sqlite.py --no-upload

sudo /opt/dosl-hub/backend/.venv/bin/python \
  /opt/dosl-hub/backend/scripts/restore_sqlite.py \
  --backup "$RESTORE_DIR/<backup>.sqlite3" \
  --checksum-file "$RESTORE_DIR/<backup>.sqlite3.sha256" \
  --destination /opt/dosl-hub/data/exhibition.db \
  --replace

# 復元スクリプトは置換前DBの所有者・権限を自動で引き継ぐが、
# サービス起動前に必ず所有者と書き込み可否を確認する
# （root所有のままだと doslhub で動くアプリが書き込めず全操作が失敗する）
ls -l /opt/dosl-hub/data/exhibition.db   # doslhub:doslhub であること
sudo chown doslhub:doslhub /opt/dosl-hub/data/exhibition.db   # 違った場合のみ
sudo -u doslhub sqlite3 /opt/dosl-hub/data/exhibition.db "BEGIN IMMEDIATE; ROLLBACK;"  # 書込確認

sudo systemctl start dosl-hub
curl --fail --silent https://34-168-97-181.sslip.io/api/health
```

復元後はログイン、展示会一覧、書類一覧、注文一覧を読み取り確認する。問題があれば
サービスを停止し、直前に退避したDBへ同じ手順で戻す。

## ディスク障害時

1. 最新の自動スナップショットから新しい永続ディスクを作る。
2. `dosl-hub` VMを停止し、復元ディスクを接続する。
3. `/opt/dosl-hub`と`/opt/dosl-hub/data`を確認する。
4. 最新の毎時SQLiteバックアップを上記手順で復元する。
5. VMを起動し、Caddy、dosl-hub、backup timerを確認する。

## 監視・通知

Cloud Monitoringで以下を構成し、同じ通知チャネルへ送る。

- HTTPS `/api/health`のUptime Check: 1分間隔、2xx、TLS検証あり
- VM稼働状態: 5分停止で通知
- ディスク使用率: 80%で警告、90%で重大
- HTTP 5xx: 5分間に1件以上で通知
- `dosl-hub-backup.service`失敗ログ: 1件で通知
- バックアップ成功ログが70分ない場合: 通知
- AI API費用: 月次予算50%・80%・100%で通知

VM指標とsystemdログの取得にはGoogle Cloud Ops Agentを使用する。通知先メールまたは
Slackチャネルは運用責任者の指定後に設定する。

## 復旧訓練

四半期ごとに、本番を停止せず次を行う。

1. GCSから無作為に1世代をダウンロードする。
2. チェックサムと`PRAGMA integrity_check`を実行する。
3. 隔離ディレクトリへ復元し、主要テーブル件数を記録する。
4. 30分以内に復元できることを確認する。
5. 結果、所要時間、担当者、失敗理由を運用記録へ残す。
